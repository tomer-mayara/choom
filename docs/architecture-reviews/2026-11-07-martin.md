# Choom architecture review through Robert C. Martin's principles

Date: 7 November 2026. Baseline: `565ecb407e119d29ed8b746ec5818e08a346ebc6`
on `codex/cr-001-t08`. This is an independent agent review informed by the
requested principles. Robert C. Martin did not participate or endorse it.
Source line numbers below refer to this baseline.

## Conclusion

Keep the architecture and improve a few boundaries. Choom already separates
its semantic model from React Flow, vendor reports, and native effects. Its
strongest objects own resources or rules, not arbitrary groups of procedures.
There is no case here for a framework rewrite, a package per directory, or
turning every exported function into a class.

The main improvements are to make the workflow's published state read-only to
consumers, make its collaborators express application roles, and enforce the
boundaries that the code already intends. Analyzer selection also needs one
owner before another analyzer is introduced. Extracting a per-load object is
worth evaluating after those changes, but is not a prerequisite for them.

This interpretation follows Martin's distinction between policy and mechanism;
his Clean Architecture description permits either objects or data structures
and functions for core rules. His later discussion of functional classes argues
for cohesion and explicitly rejects forcing every namespace of functions into
a class. These are review lenses, not rules about class counts.
([The Clean Architecture](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html),
[Functional Classes](https://blog.cleancoder.com/uncle-bob/2023/01/18/functional-classes.html))

## Structure and ownership

The dependency flow is appropriate:

```text
React controls -> LoadWorkflow -> domain rules and injected operations
                                  |                 |
                           portable document    native adapters
                                  |                 |
                            layout/render      Tauri services
```

This is a logical responsibility map, not a proposed directory tree. The actual
declarations are root `choom`, its `workspace` and `native-shell` children, and
the workspace's `architecture-model` and `desktop-adapter` children. The
[workspace manifest](../../src/component.yaml), lines 41–45, does not declare
each subdirectory as a separate component. That is correct: one declared
component may own several subdirectories.

| Area | Current responsibility | Assessment |
| --- | --- | --- |
| `src/domain/` | Ownership, relationships, semantic validation and canonical ordering | Cohesive core; preserve it. |
| `src/architecture/` | Discovery, analyzer composition, conversion and load orchestration | Useful feature grouping; make the different roles clearer without a wholesale move. |
| `src/documents/` and `src/lib/architecture-yaml*` | File lifecycle and portable format | Sound separation; the README inventory does not yet describe it fully. |
| `src/components/` and layout modules | Controls, prepared graph presentation and example | Keep React-specific projection here; no domain UI types. |
| `src/platform/` | Tauri and browser access | Keep transport validation here; identify role contracts separately from concrete access classes when consumers need them. |
| `src-tauri/src/` | Repository sessions, process jobs and owned files | Real resource boundaries; retain their distinct lifetime rules. |

The [README structure section](../../README.md), lines 306–325, omits
`src/documents/`, describes `lib/` mainly as class merging and layout, and does
not mention browser document access under `platform/`. Correct this map before
using it to justify moving code. Folder names are imperfect documentation, not
proof that components must be split.

## Design to preserve

1. **Choom owns the saved document.**
   [Architecture document validation](../../src/domain/architecture-document.ts),
   lines 25–77, checks relationships and file ownership. The
   [diagram](../../src/components/architecture-diagram.tsx), lines 37–55, projects
   the committed document into React Flow data. Layout remains separate from the
   serialized model. This is a useful boundary, not an anemic domain defect.

2. **Objects own cohesive knowledge.**
   [ComponentCatalog](../../src/domain/component-catalog.ts), lines 15–35,
   takes a declaration snapshot and answers ownership questions. Its support
   for invalid candidates during validation is deliberate and
   [characterized](../../test/unit/domain/component-catalog.test.ts), lines
   45–53. Do not make the constructor reject those candidates in the name of
   purity. `DiscoveryRun`, `ReportPaths`, and `ExecutionAttempt` likewise keep
   mutable work local to one operation. They are good examples of extraction
   based on lifetime.

3. **The analyzer strategy is already useful.**
   [ArchitecturalLayer](../../src/domain/architectural-layer.ts) isolates the
   workflow from the concrete analyzer. The
   [concrete layer](../../src/architecture/dependency-cruiser/architectural-layer.ts),
   lines 17–49, composes execution and report conversion. `ReportConversion`
   is correctly local to the dependency-cruiser implementation: another vendor
   need not adopt dependency-cruiser's report format. Keep that distinction.

4. **Cleanup is policy, not incidental error handling.**
   [DocumentFiles](../../src/documents/document-files.ts), lines 116–160,
   coalesces release operations and gates writes until release results are known.
   The native [analyzer resource owner](../../src-tauri/src/analyzer/service.rs),
   lines 46–63 and 191–236, retains resources when cleanup fails. Native
   [document storage](../../src-tauri/src/documents/mod.rs), lines 83–144,
   separately enforces snapshot limits and retirement. Do not merge these into
   a generic cleanup manager merely because all three release resources.

5. **The test split reflects real risks.**
   The workflow suites cover retained views, cancellation, retry and cleanup.
   Native services and installed acceptance cover effects that frontend doubles
   cannot prove. TypeSpec plus runtime validation protects both structure and
   semantics. This review adds no claim that all operating-system routes have
   passed; the [T08 evidence](../change-requests/CR-001-T08-evidence.md) records
   the remaining native verification limits.

## Findings

### M1 — The workflow publishes writable retained state

Priority: medium. Confidence: high about the exposure; no observed UI defect.

[LoadWorkflow](../../src/architecture/load-workflow.ts), lines 27–29 and 108,
returns its actual retained snapshot with mutable state, document, and layout
types. `publish`, lines 411–412, keeps the supplied references. A future
consumer can change `cleanupRecovery`, a relationship, or positions without
passing through a workflow operation or notifying subscribers. That weakens the
class's stated ownership of the current view and load gate.

The current React consumers read these values; this review found no in-tree
production caller mutating the returned snapshot. Treat this as an encapsulation
risk, not a claim of current corruption.

The manager then confirmed the consequence with the existing in-memory workflow
fixture: after `documentCleanupFailed()`, a load returns `busy`; changing the
returned snapshot's `state.cleanupRecovery` to `"none"` allows another load to
enter selection without cleanup. The null selector makes that load return
`cancelled`. This reproduction changed no repository files and demonstrates an
observable bypass by a consumer, not misuse by the current UI.

Start with a narrow read-only view contract, including nested collections, and
clear ownership transfer at commit. Preserve stable snapshot identity between
notifications for `useSyncExternalStore`. Do not clone the whole document on
every read. A TypeScript read-only type prevents accidental writes by checked
callers; it does not provide runtime isolation. If runtime protection is required,
specify it separately and assess a copy/freeze at the commit boundary, including
the maximum supported document size.

Following that reproduction, runtime protection should be an explicit behavior
fix in the common plan. Cache an owned, frozen document/layout view once at
commit and publish an owned read-only state value on each state change. Reuse
the committed graph during progress updates; do not traverse it on each getter
or notification. Also check returned operation outcomes and collaborator-held
references: freezing only the outer snapshot leaves those aliases able to
change nested state. Characterize current identity and cancellation behavior,
then add a failing consumer-mutation acceptance case for the corrected rule.
Measure the one-time copy/freeze against the existing size limits before
choosing its implementation.

### M2 — The load use case knows document platform mechanics

Priority: medium. Confidence: high. This is coupling, not incorrect output.

[LoadWorkflow](../../src/architecture/load-workflow.ts), lines 13–24 and 289–297,
distinguishes a desktop path from a browser reader, decides which decoder route
to use, and takes a `Pick` from concrete `DocumentFiles`. The flow is testable,
but a new source type would change the workflow's selection union and branch.
The concrete class name also owns a role that the workflow only partially needs.

Have selection return a small capability for reading the selected document,
assembled at the existing [composition point](../../src/architecture/workspace.ts),
lines 22–41. Give the workflow a named, narrow document role rather than a type
derived from the concrete service. These can be TypeScript function bindings;
no base class, container, or generic repository is needed. Keep the TypeSpec
data and error contracts; live signals and callable capabilities remain bindings
as [workflow.tsp](../../cookbook/interfaces/workflow.tsp), lines 84–86, allows.

Preserve the current cancellation differences: an unfinished native selection
must retain the load slot, and late pure browser work must not commit. Do not
hide these obligations behind a deceptively uniform method name. A proposed
capability is acceptable only if its contract makes those obligations explicit.

### M3 — Some architectural promises have no corresponding guard

Priority: medium. Confidence: high about configuration coverage.

[Dependency rules](../../.dependency-cruiser.cjs), lines 61–74, constrain files
named `load-*` and two named diagram components. There is no general rule that
prevents discovery or `src/documents/` from importing React presentation code.
The special workflow rule also depends on a filename prefix. These are future
regression paths; this review did not find such imports in the current code.

Add explicit rules for the existing application roles and their allowed
dependencies, with composition exceptions kept narrow. Do not add broad
exceptions because a type currently lives beside an adapter; relocate a role
binding only when needed to make the intended direction clear. The manager ran
`bun run check:dependencies` successfully on the baseline: 67 modules and 186
dependencies. That confirms the existing rules pass, not that every intended
boundary is enforced.

### M4 — Analyzer support is decided in more than one layer

Priority: medium before a second analyzer; otherwise low. Confidence: high.

[Discovery](../../src/architecture/repository-discovery.ts), lines 149–159,
rejects every enforcer except dependency-cruiser. The
[composition function](../../src/architecture/create-architectural-layer.ts),
lines 9–13, independently chooses the concrete implementation. The concrete
layer's own vendor check is appropriate defense at its public boundary; the
extra selection policy in generic discovery makes substitution require a change
there as well.

Put supported-analyzer selection in composition and supply discovery a narrow
support check. Keep today's early `unsupported-enforcer` discovery outcome and
session release behavior. With only one implementation, a function is enough;
do not build a plugin registry. A second-analyzer acceptance test can use a test
strategy without shipping another analyzer. Its purpose is to prove that
discovery and the workflow do not need vendor branches.

### M5 — One load attempt is a candidate for stronger ownership

Priority: low; conditional. Confidence: medium about the benefit.

[LoadWorkflow](../../src/architecture/load-workflow.ts), lines 37–50 and
187–221, stores attempt state in a mutable record whose fields are changed by
selection, analysis, commit, cleanup and disposal methods. The class also owns
workspace-wide subscription, retry selection and retained resources. These are
different lifetimes, although they cooperate in one consistency rule.

Consider a private `LoadAttempt` object that owns only operation cancellation,
completion and uncommitted candidate ownership. Keep current-view replacement,
the single load slot, and retained cleanup at workspace lifetime. This is not a
recommendation to create a class for every workflow phase. Reject the extraction
if it introduces back-and-forth callbacks, multiple owners of resource IDs, or
more places that must coordinate the final commit. Complete M1–M3 first, then
judge the remaining complexity.

## Refactoring sequence

Each step should be independently reviewable. These are proposed changes, not
work completed by this review.

| Step | Scope and completion criterion | Constraint assessment |
| --- | --- | --- |
| A — Confirm existing behavior and correct the map | Map each affected rule to existing workflow, document and installed scenarios. Correct the README ownership inventory. Retain multiple subdirectories under one declared component. | Behavioral: reuse passing characterization; add only missing cases. Observability: unchanged, still unmeasured. Architecture: document current ownership. Interface: unchanged. |
| B — Protect the published workflow view | Add a read-only consumer binding and make renderer/control inputs honor it. Preserve snapshot identity and one commit. No blanket deep clone. | Behavioral: characterize identity, retained view and cancellation; runtime mutation prevention would be a separate specified change. Observability: unchanged. Architecture: no new component. Interface: update TypeScript live binding and boundary notes; TypeSpec wire data stays unchanged unless its meaning changes. |
| C — Remove document platform decisions from orchestration | Compose a selected-document reader and an explicit document role. Keep the same decode errors, cancellation semantics, retry selection and cleanup gate. | Behavioral: existing browser/desktop open, invalid YAML, cancel and retry scenarios remain green. Observability: preserve stages and durations. Architecture: add application dependency rules. Interface: derive serializable data from TypeSpec; document callable bindings. |
| D — Centralize analyzer selection | Inject the supported-enforcer policy from composition; retain the concrete layer's vendor validation. No registry. | Behavioral: preserve unsupported discovery failure and cleanup; demonstrate substitution through discovery and workflow. Observability: unchanged stages. Architecture: forbid concrete analyzer knowledge outside its adapter/composition. Interface: retain TypeSpec outcomes or update them explicitly if required. |
| E — Decide whether an attempt object helps | Evaluate M5 after B and C. Proceed only if cancellation and candidate ownership gain one clear owner with fewer coordination points. Otherwise record a deliberate deferral. | Behavioral: passing characterization first, then all cancellation/cleanup suites. Observability: unchanged. Architecture: an internal helper, not an automatic new declared component. Interface: no new public boundary unless proven necessary. |

Use the repository's behavior-preserving refactor sequence: establish passing
characterization before moving structure. New behavior or a corrected defect
needs Gherkin and a focused failing test first; do not manufacture a failing
acceptance test for unchanged behavior. Apply all four cookbook constraints,
but do not create artifact churn where a constraint remains unchanged.

For production changes, run affected suites, `bun run check`,
`bun run check-types`, the relevant build, and `bun run habit-hooks --all`.
Changes to Rust require its behavior, formatting and Clippy checks; changes to
the assembled desktop route require packaged acceptance. Keep native platform
limits explicit. For these review documents, inspect links and text rather
than claiming a behavior test validates the prose.

## Changes deliberately excluded

- No package split, framework migration, inheritance tree, or global event bus.
- No forced object wrapper around canonicalization, IDs, YAML conversion, or
  deterministic graph calculations.
- No generic IPC/cleanup abstraction based only on repeated `try`/`catch` or
  release code. The owners have different failure and lifetime rules.
- No immediate Rust file split just to reduce line count. Its current service,
  process, file and model boundaries are meaningful; preserve the locks and
  resource order if a later concrete change calls for extraction.
- No removal of the example or retained directory picker as a disguised
  refactor. Those are observable product decisions requiring their own change.

## Discussion with the Metz-principles reviewer

The two reviewers exchanged critiques after completing their independent
documents. This records agent discussion, not a conversation between the named
authors. The [Metz review](2026-11-07-metz.md) and the manager's runtime
reproduction changed the execution priorities above.

### What I challenged

**Read-only typing is insufficient for M1.** The Metz draft initially proposed
a narrow read-only binding and a separate decision about runtime protection.
The reproduced cleanup-gate bypass makes runtime ownership a current behavior
fix. The Metz reviewer agreed and revised that position. We agreed to own copies
of published values before freezing them, rather than freezing collaborators'
objects in place. Protection must cover nested state, operation outcomes,
document collections and metrics, and layout positions. Tests must also mutate
references retained by a collaborator after commit. Copy the committed graph
once and reuse it; state changes must not repeatedly copy the graph.

**The safe-diagnostic fix should remain small.** I accepted the Metz finding in
[architecture-yaml.ts](../../src/lib/architecture-yaml.ts), lines 14–38 and
46–53: the codec duplicates domain wording and relies on exact matching. We
compared named safe constants with an issue-ID protocol; the Metz draft already
allowed the smaller option. Both reviewers agreed that one domain-owned catalog
and explicit priority are sufficient now, preserving current messages, privacy
filtering and public error codes. Stable internal issue IDs are conditional on
a demonstrated need; no new serialized diagnostics or global error framework
is justified.

### What I conceded

**Do not extract the selected-document capability now.** My independent plan
put this before analyzer selection. The Metz reviewer pointed to the different
waiting and cancellation obligations in
[load-workflow.ts](../../src/architecture/load-workflow.ts), lines 224–230 and
289–297, and its cancellation tests. A uniform reader can move the branch while
hiding those obligations. I accept keeping the two-case branch for now. Revisit
it for a third document source, changed read/retry semantics, or repeated
host-driven workflow edits. Any future role must preserve the native load-slot
obligation and rejection of late browser work without policy flags spread
across callers.

**Analyzer support injection is preparation for a real replacement.** Both
reviewers favor one composition-supplied support policy before a second enforcer
is introduced. We do not require it in the immediate cleanup work. The future
change must retain the early `unsupported-enforcer` discovery outcome and
session release, and preserve defensive checks inside the concrete strategy.
One policy function is enough; a registry remains excluded.

**Defer `LoadAttempt`.** The current controller coordinates a real transaction.
Its length alone does not prove a missing object. I accept the Metz argument
that an extraction which shares flags, callbacks or resource IDs would move
complexity without reducing it. Revisit only for a concrete behavior change,
with explicit ownership transfer and fewer coordination points.

### Agreed minimum plan

1. Correct the ownership map and record resource/transition invariants using
   existing characterization. Preserve the declared component tree and its
   multiple-directory ownership semantics.
2. Fix runtime publication ownership and expose the narrow view role. Treat
   mutation isolation as an explicit behavior correction with Gherkin and a
   failing test, while keeping identity, cleanup, cancellation and retry
   characterization green.
3. Give safe semantic messages and their priority one owner. Preserve external
   error behavior and TypeSpec contracts; use passing characterization before
   this structural change.
4. Add targeted dependency rules for the agreed application and codec boundaries.
   Verify representative allowed and forbidden imports; do not infer additional
   components or split packages to make the rules easier.

The shared plan should supersede the independent sequence where these priorities
differ. It must retain all four cookbook assessments, distinguish live TypeScript
bindings from TypeSpec data contracts, measure one-time snapshot-copy cost within
current limits, and state the existing native acceptance gaps honestly.
