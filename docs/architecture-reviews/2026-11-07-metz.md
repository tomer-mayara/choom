# Architecture review through Sandi Metz's design principles

This is an independent agent review informed by Sandi Metz's published ideas and
the design lens requested by the user. Sandi Metz did not review or endorse Choom.

Reviewed on 2026-11-07 at commit
`565ecb407e119d29ed8b746ec5818e08a346ebc6`, branch `codex/cr-001-t08`.
Line references below refer to that commit. This review precedes the discussion
with the Martin reviewer and makes no production changes.

## Conclusion

Keep the architecture. Improve a few messages and boundaries before adding more
objects. Choom already has useful objects that own state and lifetimes, a portable
data model, and explicit composition. The main risks are knowledge that crosses
boundaries informally and the difficulty of changing a resource transaction safely.
The reviewed code does not justify a new framework, package split, or class for
each calculation.

This judgment applies two ideas: callers should depend on the messages a role
supports, and shared code must represent shared meaning rather than superficial
similarity. These are interpretations of
[What Does OO Afford?](https://sandimetz.com/blog/2018/21/what-does-oo-afford)
and [The Wrong Abstraction](https://sandimetz.com/blog/2016/1/20/the-wrong-abstraction),
not a prediction of the author's verdict on this repository.

## What the system owns

| Area | Actual responsibility | Assessment |
| --- | --- | --- |
| `src/domain/` | Declared ownership, observations, semantic documents, validation, and starter data | The semantic model is independent of rendering and native access. Keep records for portable data and functions for transformations. |
| `src/architecture/` | Discovery, analysis composition, loading, and workspace composition | Several responsibilities share one declared workspace component. This is legitimate; each folder need not become a component. |
| `src/architecture/dependency-cruiser/` | Vendor report interpretation and the matching execution strategy | A useful isolation boundary. Vendor details are expected here. |
| `src/documents/` and YAML code in `src/lib/` | Snapshot ownership, file workflows, and format validation | These are different responsibilities with different lifetimes. Their separation is useful even though the ownership map understates it. |
| `src/components/` and `src/App.tsx` | User interaction and rendering prepared data | Function components fit the framework. Business workflow state is outside React. |
| `src/platform/` | Host detection, native dialogs, validated IPC, and browser files | An adapter boundary, although the declared name `desktop-adapter` is narrower than its current contents. |
| `src-tauri/src/` | Repository identities, analyzer jobs/processes, file ownership, and native command boundaries | OS resource semantics warrant dedicated owners. Rust modules and structs already express them. |
| `cookbook/`, `scripts/`, and `test/` | Constraints, generation/checks, and verification | These are not extra application services. Keep them out of the runtime dependency graph. |

The declarations in [src/component.yaml](../../src/component.yaml), lines 41–45,
give the workspace child boundaries for the domain and platform. The remaining
workspace directories still belong to one declared component. A source directory
is an organizational choice, not proof of a separate component. Preserve the
deepest-declared-owner rule in
[ComponentCatalog](../../src/domain/component-catalog.ts), lines 28–35, including
one component owning several subdirectories.

## What should stay

- `ComponentCatalog` owns a private declaration snapshot and answers ownership
  questions. It does not force clients to reconstruct the prefix rules. The
  [mutation and ownership tests](../../test/unit/domain/component-catalog.test.ts),
  lines 5–29, demonstrate why this is a useful object.
- `RepositoryDiscovery` keeps reusable collaborators separate from each
  `DiscoveryRun`'s traversal state. See
  [repository-discovery.ts](../../src/architecture/repository-discovery.ts),
  lines 33–98. This is preferable to putting mutable traversal state on a singleton.
- `ArchitecturalLayer`, `DepCruiserExecution`, and `ReportConversion` describe
  actual roles. [The concrete layer](../../src/architecture/dependency-cruiser/architectural-layer.ts),
  lines 17–49, composes matching execution and conversion. The latter two are
  intentionally vendor-local; replacing the whole analyzer uses the neutral layer.
  A universal report protocol is not required now.
- [DocumentFiles](../../src/documents/document-files.ts), lines 44–160, owns
  release coordination. Its active releases and retained failures are different
  facts. Do not replace them with a generic asynchronous queue merely to reduce
  code. Native storage remains the authority over filesystem effects.
- [The workspace composition function](../../src/architecture/workspace.ts),
  lines 21–71, selects browser and desktop behavior and creates the shared owners.
  Two explicit host branches are cheaper to understand than a plugin registry.
- [The diagram](../../src/components/architecture-diagram.tsx), lines 37–75,
  consumes a semantic document and prepared positions. React Flow remains a view,
  and [the layout function](../../src/lib/architecture-layout.ts), lines 8–31,
  remains an ordinary calculation with an explicit asynchronous collaborator.
- Native `RepositoryLease`, analyzer `Resources`, and document `OwnedFile` model
  real capabilities and cleanup obligations. See
  [repository.rs](../../src-tauri/src/repository.rs), lines 146–176,
  [analyzer/service.rs](../../src-tauri/src/analyzer/service.rs), lines 30–63,
  and [documents/files.rs](../../src-tauri/src/documents/files.rs), lines 118–130.
  A shared filesystem superclass would hide meaningful differences in ownership,
  process cleanup, overwrite consent, and error behavior.

## Findings

### M1 — Validation wording is an undeclared protocol

**Priority: medium. Confidence: high. Maintenance defect; no demonstrated current
user failure.**

[architecture-yaml.ts](../../src/lib/architecture-yaml.ts), lines 14–38 and 46–53,
copies safe domain error messages and recognizes failures by exact string equality.
Those strings originate in, among other places,
[component-catalog.ts](../../src/domain/component-catalog.ts), lines 38–65, and
[architecture-document.ts](../../src/domain/architecture-document.ts), lines 25–66.
Changing the domain's wording can silently turn a precise saved-document error
into a generic schema error. The codec has to know how another owner phrases its
explanation, rather than what failed.

Use one narrowly scoped catalog of safe semantic diagnostics, with stable identity
and explicit display priority. Keep the current external codes and messages. The
smallest adequate implementation may use shared named message constants; introduce
internal issue identifiers only where they remove a real dependency on prose.
Do not create a global error framework or a hierarchy of exception classes. Keep
untrusted parser text and filesystem paths out of user messages.

### M2 — The view's collaborator is wider than its role

**Priority: medium. Confidence: high. Coupling risk, not a demonstrated UI defect.**

[WorkspaceBinding](../../src/architecture/workspace.ts), lines 16–19, exposes
`LoadWorkflow` itself. [App](../../src/App.tsx), line 17, needs subscription and
snapshot messages; [WorkspaceControls](../../src/components/workspace-controls.tsx),
lines 43–90, needs load, cancel, retry, and cleanup messages. The concrete class
also exposes lifecycle disposal and the exporter's cleanup notification. Its
private fields make arbitrary structural substitutes incompatible with the class
type even when they provide the required public messages.

Define the consumed view role as a TypeScript binding derived from the existing
TypeSpec operations plus subscription/snapshot methods. Keep the concrete workflow
inside composition. This is one useful interface at a real consumer boundary,
not a mandate to create interfaces for every class. Do not widen the public API
or add a second independently authored data contract.

The snapshot currently returns the owner's mutable object directly:
[load-workflow.ts](../../src/architecture/load-workflow.ts), lines 27–30 and 108.
Current view consumers only read it; no corruption was observed. As part of this
small boundary change, express a read-only view in TypeScript. Do not claim that
shallow `readonly` provides deep runtime immutability, and do not clone the graph
on every React snapshot read. Freezing or copying at commit needs a separate cost
and compatibility decision if runtime protection becomes a requirement.

### M3 — Workflow refactoring has a high chance of moving complexity around

**Priority: watch; characterize before extraction. Confidence: high on coupling,
medium on the value of any extraction.**

[LoadWorkflow](../../src/architecture/load-workflow.ts), lines 37–49 and 87–102,
holds operation state, committed-view state, repository safety, and cleanup state.
Its repository path, lines 233–286, also creates the analyzer, translates failures,
closes the repository, and prepares the candidate. This is the likely pressure
point as new behavior arrives.

These responsibilities are not all independent reasons to split a class today.
The atomic view commit and cleanup gate are one transaction. Moving each stage
into an object that exposes setters would produce procedural code spread across
more files. In particular, document cleanup is coordinated with an independent
export through [workspace.ts](../../src/architecture/workspace.ts), lines 45–52,
and a revision check in
[load-workflow.ts](../../src/architecture/load-workflow.ts), lines 361–378.
Deleting that check because the document service has its own state loses a
different invariant: an older cleanup result must not clear a newer failure.

Before extraction, make an ownership/transition table and run the existing
[cleanup](../../test/unit/architecture/load-workflow-cleanup.test.ts) and
[document concurrency](../../test/unit/documents/document-files-concurrency.test.ts)
characterization. If a later change needs a repository-load collaborator, it must
own the complete repository lifetime and return an outcome with explicit resource
transfer. Keep one owner for commit, cancellation, and load exclusion. Stop the
extraction if it requires shared mutable flags or callbacks that reconstruct the
original controller elsewhere.

### M4 — The ownership map is stale and the import checks are narrower than prose

**Priority: low for documentation; medium when moving code. Confidence: high.**

[README.md](../../README.md), lines 306–326, omits `src/documents/`, describes
`lib/` as only class merging and layout, and understates document/browser work in
`platform/`. Correct these descriptions before using the tree to justify moves.

The codec rule in [.dependency-cruiser.cjs](../../.dependency-cruiser.cjs),
lines 31–38, permits any `src/lib/` import. The load rule, lines 61–67, selects a
filename prefix. Neither is a general proof that future codec helpers or renamed
workflow helpers stay isolated. These are guard gaps, not observed forbidden
dependencies. Tighten only the approved responsibilities and verify representative
allowed/forbidden edges when changing the configuration. Do not convert every
folder into a declared component to obtain a neater diagram.

## Refactoring plan

Execute each step separately; the first three steps are useful now. Step 4 is a
decision gate, not approval for a large rewrite.

### Step 1 — Correct the ownership map and record the transaction

Update the README tree and component descriptions where inaccurate. Record who
creates, retains, transfers, and releases repository sessions, analysis jobs,
candidate snapshots, current snapshots, and temporary export files. Show the
commit point and the distinction between retryable cleanup and restart-required
uncertainty. Keep the current manifest hierarchy and directory structure.

**Behavioral:** map existing Gherkin and characterization to these invariants;
change no accepted outcomes. **Observability:** record the existing unmeasured
OpenSLO limitation; no new telemetry or SLO claim. **Architecture:** amend only
descriptions; inspect current dep-cruiser coverage. **Interface / TypeSpec:**
retain contracts; correct boundary notes if the ownership table exposes drift.
Validation is document/link review and the full Habit Hooks scan.

### Step 2 — Replace the codec's copied semantic message knowledge

Characterize current diagnostic choice, ordering, and privacy through the public
codec. Give semantic diagnostic identity and safe display text one domain owner,
then update domain validators and codec translation together. Keep the YAML v1
shape, external failure codes, and message behavior unchanged.

**Behavioral:** retain saved-file rejection Gherkin; use passing characterization
before changing structure. Specify a separate red scenario only if a real behavior
defect is discovered. **Observability:** no new events or OpenSLO change.
**Architecture:** retain domain independence and codec isolation; assess the
existing rule against new imports. **Interface / TypeSpec:** public contracts
remain unchanged; run conformance checks. Validate domain/codec tests, affected
Cucumber cases, `bun run check`, `bun run check-types`, and `bun run build`.

### Step 3 — Narrow the view-facing workflow role

Introduce the consumed TypeScript role without wrapping `LoadWorkflow` in another
runtime object. Derive operation types from TypeSpec. Keep subscription and view
data in the explicitly documented TypeScript binding. Separate view access from
composition-only cleanup notification and lifetime control. Express read-only
consumer intent without changing snapshot identity or copying on each read.

**Behavioral:** characterize UI progress, retry, cancel, export independence, and
snapshot identity; preserve existing Gherkin. **Observability:** unchanged.
**Architecture:** make the UI depend on the role, with a specific guard only if
needed to enforce that boundary. **Interface / TypeSpec:** change TypeScript
bindings and boundary notes; change TypeSpec only if an operation/data contract
actually changes. Validate DOM, workflow, interface, and affected browser tests,
then the full required TypeScript checks and frontend build.

### Step 4 — Reassess extraction against a concrete change

After steps 1–3, attempt a private repository-load owner only if its complete
lifetime can move behind useful messages. Retain the current design otherwise.
No generic pipeline, event bus, state-machine package, universal native service,
or runtime analyzer registry is part of this plan.

**Behavioral:** preserve cancellation, stale-result exclusion, commit atomicity,
cleanup priority, and retry selection through existing characterization.
**Observability:** preserve stage/outcome reporting. **Architecture:** update
dep-cruiser rules for actual new helper paths and keep one composition root.
**Interface / TypeSpec:** retain existing outcomes and YAML; document resource
transfer if a new boundary is accepted. Native changes require Cargo tests,
formatting, Clippy, desktop packaging, and installed acceptance in addition to
the affected frontend checks. Do not introduce native changes just to enable
a TypeScript rearrangement.

For each production step, run `bun run habit-hooks --all` on the complete
candidate, keep snoozes empty, and update affected cookbook links. A passing
dependency check is not behavior verification. The manager ran
`bun run check:dependencies` at this baseline: 67 modules and 186 dependencies
passed the existing rules. This review inspected code and tests; it did not
rerun native or browser acceptance and does not close the platform gaps recorded
in [T08 evidence](../change-requests/CR-001-T08-evidence.md).

## Explicit deferrals

Keep Zod runtime semantics alongside generated TypeSpec shapes. Do not replace
semantic validation with schema compilation. Keep the starter graph and imported
document paths separate until a real requirement makes their differing layout and
presentation policies converge. Keep the current workspace singleton outside React
render; a multi-window lifecycle design is unnecessary for the current main-window
contract. Avoid consolidating the three IPC adapters merely because their
validation/transport skeletons look similar: progress, failure mapping, timing,
and response cardinality differ. Apply DRY3 to proven shared behavior, not syntax.

## Discussion with the Martin-principles reviewer

This section records the later agent discussion. The independent assessment above
is retained so that changes of position are visible. Neither author participated.

### Concession: runtime snapshot ownership needs a behavior fix

The manager reproduced a concrete consequence of the writable snapshot with the
existing in-memory workflow fixture:

1. Call `documentCleanupFailed()`; the next load returns `busy`.
2. Change the returned snapshot's `state.cleanupRecovery` to `"none"`.
3. The next load enters selection without cleanup recovery. Its null selection
   makes the result `cancelled`.

No current UI caller was observed doing this. However, it demonstrates that a
consumer can bypass an owner-enforced gate through the public snapshot. My initial
recommendation for read-only consumer types is insufficient to enforce that rule
at runtime. I accept the Martin reviewer's request to specify and test a runtime
ownership fix separately from behavior-preserving refactoring.

The smallest sound common design owns and freezes small published state and
outcome values, and takes an owned, frozen document/layout snapshot once at commit.
Repeated getters return the same snapshot between notifications. Progress updates
reuse the committed graph. Do not clone or traverse it on each read, and do not
freeze a collaborator's mutable objects in place. Cover aliases through returned
operation outcomes and retained document/layout inputs, not just direct writes
through `getSnapshot()`. Check maximum-supported document cost and the real React
Flow consumer before choosing the copy/freeze implementation.

This change needs an observable Gherkin scenario and a failing focused test for
the corrected invariant. Existing identity, cancellation, cleanup, and export
characterization stays green. TypeSpec wire shapes need not change merely to
express read-only live bindings; update boundary notes and conformance coverage.

### Agreement: use one safe diagnostic catalog before introducing issue IDs

The Martin reviewer accepted M1 and proposed domain-owned named safe constants
with the current explicit priority order. I agree. This removes the copied prose
dependency with less machinery than a new issue protocol. Stable internal IDs
remain an option if a concrete consumer needs them; new public error codes,
localization infrastructure, and a global error framework are out of scope.
Preserve the present codec messages, failure categories, and privacy behavior.

### Pushback: a uniform selected-document reader can hide unequal lifetimes

The Martin review proposes returning a selected read capability so the workflow
does not distinguish desktop paths from browser readers. That is a plausible
future role, but the two current branches deliberately wait differently:
[savedDocument](../../src/architecture/load-workflow.ts), lines 289–297, waits
for the desktop read and races the pure browser read against cancellation. The
selection and retry rules also retain different values. Moving this knowledge
behind an innocently uniform `read(signal)` name does not remove it.

I recommend deferring the extraction until a third source, changed read/retry
semantics, or repeated source-specific workflow edits justify it. Its future
contract must retain the native load slot until required work finishes and prevent
late browser results from committing, without policy flags or duplicate
cancellation owners. A narrow view-facing workflow role is useful now and does
not require this source abstraction.

### Agreement: centralize analyzer selection only when it becomes useful

The independent Martin review correctly identifies that generic discovery rejects
non-dependency-cruiser enforcers while composition separately chooses the layer.
A composition-supplied support predicate is the preferred small change before
adding another enforcer. Preserve early `unsupported-enforcer` failure, session
release, and the concrete layer's defensive vendor check. With one analyzer,
this is a lower-priority extension point, not an existing import failure and not
a reason to build a registry.

### Agreement: keep extraction conditional

Both reviews reject immediate stage-by-stage objects or a generic cleanup engine.
The proposed `LoadAttempt` or repository-load owner must move a complete lifetime
behind useful messages and reduce coordination points. The existing atomic commit,
single load slot, newer-cleanup-failure protection, and native resource authority
must each retain one owner. If those conditions cannot be shown, retain the
current controller and its characterization tests.

The proposed common sequence is: correct ownership documentation and map existing
coverage; fix published snapshot ownership while narrowing the consumed role;
centralize safe semantic diagnostics; strengthen specific dependency guards.
Analyzer selection and document-source abstraction stay conditional, and any
attempt-object extraction is reconsidered only against a concrete change.
